前一段时间在做基于 Qwen3-ASR 的语音识别系统，为了处理大量专有名词、人名、产品型号这类"难词"，顺着 AmphionASR 的技术路线搭了一套热词召回模块。这篇文字主要记录我在复现和训练这个召回模块过程中的一些理解、配置和踩过的坑。笔者不是做对比学习出身的，很多东西是边看论文边试出来的，如有疏漏欢迎指出。

> 相关论文：AmphionASR（Amphion Team, 2026.07.28） · [Contextual Biasing for LLM-Based ASR with Hotword Retrieval and RL（arXiv:2512.21828）](https://arxiv.org/abs/2512.21828)

## 说在前面

先说清楚这个模块要解决什么问题。基于 LLM 的 ASR 系统在通用转写上已经很强了，但遇到"某个只在特定领域出现的专有名词"时依然容易出错——因为这个词在整个训练分布里出现次数太少，模型没有足够的先验。最直接的解法是把候选词表塞进 prompt，但这样做有两个问题：一是候选词表可能几万甚至几十万条，直接撑爆上下文；二是把大量无关词一次性喂给 decoder，反而会诱导模型产生幻觉。

所以工业界的常规做法是**两段式**：先用一个检索模块从大词表里"捞"出跟当前这句话最相关的一小撮候选词（比如 top-50），再把这几十个词拼进 prompt。这篇笔记讲的就是第一段——这个检索模块怎么训练。

AmphionASR 的做法是复用 GLCLAP 的框架：冻结的音频塔 + 冻结的文本 embedding 表，中间加两个小小的 MLP 适配器，把两者投影到同一个空间里做对比学习。整个模块的可训练参数只有 500 万出头，相比 17 亿的基座可以忽略不计，训练成本非常低。

## 整体结构

召回模块的结构非常简洁，本质上是 CLAP 那套"双塔对齐 + 内积打分"的思路，配上 GLCLAP 的局部细粒度设计。

音频侧先经过冻结的 Qwen3-ASR 音频塔得到帧级特征（每帧 2048 维），再经可训练的音频适配器投影成 512 维的帧向量；文本侧把热词送进冻结的 LLM token embedding 表（同样是 2048 维），做均值池化之后经可训练的文本适配器也得到 512 维向量。两者的匹配程度就用 max-over-time 余弦来衡量。

两个适配器的结构完全一致，都是一层 LayerNorm，接一个把维度压到 1024 的线性层，过 GELU 激活，最后再降到 512。音频侧和文本侧的输入维度都是 2048（1.7B 模型的 LLM hidden 大小）。加上一个可学习的温度参数，可训练参数总共 **5,254,145** 个。

这里有个工程上的小优化值得一提：原始实验里保留了完整的 `thinker` 对象，但检索实际上只用到音频塔和 token embedding 表两张。把用不到的 LLM decoder 层丢掉之后，打分结果完全一致，但训练和推理时占用的显存显著下降。这件事在显存紧张的时候还挺重要的。

### 论文原话

> Following GLCLAP [19], AmphionASR retrieves hotwords with a fine-grained local scoring module (Figure 3) that reuses the frozen audio encoder and the frozen LLM text embedding table. Two small trainable MLP adapters map these frozen representations into a shared 512-dimensional space; the audio side is kept at the frame level (no utterance-level pooling), and each candidate hotword is scored against every frame,
>
> a_t = g_audio(AuT(x)_t), k_h = g_text(E_tok(h)), s_h = max_t a_tᵀ k_h, H′ = TopK_{h∈H} s_h. (1)

## 打分函数：为什么要 max-over-time

这是整个模块里最值得琢磨的一个设计。普通的 CLAP 是把整段音频池化成一个向量，再跟文本向量算余弦。但这个做法用在热词检索上有个致命问题：

> Applied to hotword retrieval, pooling the whole utterance into one audio token yields a global query without explicit temporal locality. This representation can obscure hotwords that occupy only short spans of a longer utterance.

翻译过来就是：如果一段音频有 60 秒，而目标热词只出现在第 47 秒的 0.8 秒里，把整段音频压成一个向量之后，这 0.8 秒的信息会被其余 59 秒彻底稀释掉。

AmphionASR/GLCLAP 的做法是**不池化**，音频侧保持帧级别，让每个热词跟**每一帧**都算一次相似度，然后取时间维度上的最大值：

$$s(a, h) = \max_t \langle a_t, k_h \rangle$$

这个 max-over-time 的含义很直观：**只要音频里有任何一帧跟这个热词很像，这个热词就能拿到高分**。它把"整段是否匹配"变成了"是否存在某一段匹配"。

这个设计在长音频上非常有效，但也带来了一个副作用，后面讲阈值标定的时候会详细说——**音频越长，max 操作撞出高分的机会越多**，所以干扰词的分数上限会随音频长度水涨船高。

## 损失函数：全局 + 局部，双向对比

损失函数沿用 GLCLAP 的 global–local 双向对比结构，一共四项：

全局分支拿整段音频池化后的向量去对齐完整转写文本；局部分支拿每一帧的音频向量去对齐热词文本，用的是 max-over-time 相似度。每个分支都算 audio→text 和 text→audio 两个方向，各自一个交叉熵，再取平均，最后把两个分支的损失相加。

全局分支负责"这段话整体在讲什么"，局部分支负责"这段话里具体出现了哪个词"。两个分支互补。

这里有个容易出错的细节。同一个 batch 里各条音频长度不同，短音频右侧会补上 padding 帧，求均值时必须把这些帧排除掉——只在有效帧上求和，再除以有效帧数。否则补齐的零向量会把均值拉偏，而且音频越短受的影响越大。

### 温度参数的坑

温度是可学习的，论文里初始化在 0.07。这里有个 CLIP 风格的约定问题：按 CLIP 的写法，代码里存的并不是温度本身，而是温度的倒数再取对数，也就是约 2.66，前向时再取指数还原回温度。

我在复现的时候踩过一个坑：早期代码里直接把 0.07 存进去了，而前向计算时会对这个值取指数。结果是实际生效的温度变成了约 0.932，而不是应有的 0.07——**温度高了大约 13 倍**。这个 bug 不会让训练崩溃（loss 照样下降），但会明显削弱对比学习的"锐度"，让负样本压不下去。因为这种错误是**静默**的，很难从 loss 曲线上看出来，所以特别值得检查一下自己代码里这个值到底是温度还是 logit_scale。

### 论文原话

> We build the retrieval objective upon GLCLAP [19], adopting its global–local bidirectional contrastive loss: a global term aligning pooled audio with the transcript and a local term aligning each hotword with per-frame audio via a max-over-time similarity, each summed over the speech→text and text→speech directions. Our only deviation is the positive/negative selection of the local branch.

注意最后一句——**唯一的偏离就在负样本选择上**，这正是下一节要讲的。

## 负样本设计：这个模块的核心

对比学习的效果几乎完全取决于负样本的质量。in-batch negatives 是最省事的做法（同一个 batch 里其它样本的正样本天然就是负样本），但它有个明显的上限：负样本数量受限于 batch size。有效 batch 128 就只有 127 个负样本，对于几十万词的大词表来说远远不够。

AmphionASR 的做法是从**热词池**里采样负样本：

> The positive for each utterance is its ground-truth hotword; instead of GLCLAP's in-batch negatives, we sample N=4095 negatives per utterance from the same-language hotword pool, excluding the batch's own hotwords and shared across the batch so that the negative embeddings are encoded only once per step. The text→speech direction keeps in-batch audios as candidates.

这段话里有几个设计要点：

1. **N=4095 个负样本**，远大于 batch size，负样本信号强得多；
2. **同语言采样**——中文 query 只用中文池的负样本，英文只用英文池；
3. **整个 batch 共享同一组负样本**，这样负样本 embedding 每步只需要编码一次，省掉大量重复计算；
4. **排除 batch 自身的 hotwords**，避免把正样本当成负样本；
5. **text→speech 方向仍然只用 in-batch 音频**，保持与 GLCLAP 对称结构一致。

第 2 点其实是我实操中改动过的地方。早期实现里负样本是中英混着采的，结果中文 query 经常把英文词排到前面——不是因为模型学错了，而是因为跨语言本来就不该在这个空间里比较。改成按行取同语言负样本之后，中文检索的表现明显变好。

### 单向子串安全

还有一个容易被忽略的细节：**假负样本**。

假设某个词的标注是 "High NA"，而热词池里同时存在 "NA"。归一化之后（去掉空格、转小写）分别是 `highna` 和 `na`——显然 `na` 是 `highna` 的子串。如果音频里说的是 "High NA"，那这段音频**实际上确实包含了 "NA" 的读音**。此时如果把 "NA" 当负样本，就是在惩罚模型做出正确的判断。

所以剔除规则必须是**单向**的：

- **b 是 a 的子串 → 剔除**：音频说 a 时必然包含 b 的读音，这是假负样本；
- **a 是 b 的子串 → 保留**：b 更长、并未真的出现，恰恰是最理想的难负样本。

也就是说，这个判断必须是单向的，两个方向的处理方式刚好相反。

### 难负样本挖掘

除了随机采样，为了提高训练效率，还预先离线挖掘了一批容易被混淆的难负样本，每个词保留 top-10。挖掘的依据是词形相似度：主体是字符二元组的 Jaccard 相似度（权重 0.7），再混入一点字符重叠率（权重 0.3）。

采样时的优先级是：**离线难负表 → bigram 索引的在线候选 → 随机词补齐**，三级回退。中文场景下还可以考虑拼音相近的词（比如"张三"和"张珊"），这类负样本因为是同音词，对模型来说区分难度更大，训练价值也更高。

### 实体冲突感知 batch

还有一个细节：如果同一个 batch 里出现了两条音频，它们的标注实体恰好是同一个词，那么在 in-batch 负样本的视角下，这两个样本会互相把对方的正样本当成负样本——又是一个假负样本问题。

为此我实现了一个实体冲突感知的 batch 采样器：在保证效率的前提下，尽可能让同一个 batch 内的实体互不重复。做法是按"冲突度"（一行的实体在全局出现的次数）降序，贪心地把每行塞进最近一个"实体集合无交集且未满"的 batch 里。

多卡训练时，还需要把实体取模分配到不同 rank 上，保证跨卡也不会冲突。不过这里有个已知的不完美之处：分区是按**每行的第一个实体**做的，多实体行理论上仍然可能通过次要实体跨 rank 冲突。这是原始实验的行为，为了保持实验轨迹一致我保留了它，没有做静默修正——但这种地方其实是后续可以改进的点。

## 数据构建

召回模块的效果对数据质量极其敏感。我在整个项目上最大的一个结论就是：

> **带真实实体标注的数据，效果远好于用随机子串凑出来的数据。**
>
> 早期我用 LibriSpeech 的转写随便切一些子串当"实体"来训练，recall@1 只有很低的水平；换成真实标注的实体数据之后，高了一个数量级。

### 实体抽取

真实实体标注是用 LLM 批量抽出来的。用的是 `Qwen/Qwen3.5-4B`，通过本地 vLLM 起 OpenAI 兼容服务，温度设为 0、关闭 thinking，prompt 固定（SHA256 校验过）。如果读者可以启动更大的LLM进行实体抽取，自然是更好的。

抽取的类别主要是这几类：

| 类别 | 说明 | 例子 |
|---|---|---|
| 人名 | 优先级最高，ASR 最难处理 | 王志强、Buster Keaton、Dvorak |
| 具体地名 | 非常见的、易错的 | Chaoyang Park、Arkansas、Jaipur |
| 机构/品牌 | 公司、学校、产品品牌 | Tsinghua University、Starbucks、NATO |
| 领域术语 | 技术、法律、科学名词 | blockchain、勾股定理 |
| 产品型号 | 中英混合、含数字的型号 | 小米SU7、iPhone 15、RTX 4090、A320 |
| 技术缩写 | ASR 容易拆开或读错 | GPU、BERT、API、RTX |

同时明确排除：高频普通名词、常见动词形容词、裸数字和时间、语气词虚词、单字词、以及最常见的国家和首都名（这些 ASR 本来就能处理好）。

一个实用的小经验：**提示词里要明确写"拿不准就抽"**。因为漏掉一个真热词的代价（ASR 转错）通常大于多抽一个边界词的代价（候选池大一点），所以偏向召回率更划算。另外 prompt 里最好加一条：抽取时保持**原语言和原字形**，不要翻译——尤其像"小米SU7"这种中英混合的写法，本身就正是 ASR 最容易翻车的地方。

以下是抽取 prompt 里的核心判据：

> Extract words that **could easily be mis-transcribed by an ASR system based on pronunciation alone, without context**.

这个判据我觉得是整个 prompt 里最关键的一句，它把"什么是热词"定义得非常清楚：**脱离开上下文、光靠发音就可能被写错的词**。

这里补充一个选型上的说明。整个流程**最终统一使用的是 `Qwen/Qwen3.5-4B`**，发布出去的索引全部由这个模型生成。

前期我确实拿 `Qwen3-1.7B` 做过对比实验，原因是它更快（单卡吞吐大约是 4B 的几倍），一开始想着"英文用小的、中文用大的"来省时间。但实际对比下来，小模型对中文短指令（比如"请搜索我附近的超市"）容易整句抽取或误抽，而且在"该不该抽"这个判断上明显更松。考虑到实体标注是一次性成本、而标注质量会直接影响后面整个召回模块的上限，最后没有采用混合方案，而是**统一用 4B 跑全量**。

### 视频数据

除了现成的语音数据集，另一部分数据来自公开技术讲座、评测视频的语音切片。下载和字幕处理用的是 `yt-dlp`，配合一套多进程并行的下载脚本。

**动手批量下载之前，我会先去看一看目标博主的主页，观察他的字幕情况再决定要不要批量抓。** 这一步能省掉大量无用功，因为不同博主的字幕供给差异极大：有的全程有人工字幕（CC），有的只有平台自动字幕，还有的干脆一个字幕都没有。对最后一类，切分和对齐就无从谈起（除非自己跑一遍 ASR），所以会直接跳过。观察的指标主要有几个：

- 视频列表里带不带 CC 标记、人工字幕的覆盖率大概多少；
- 字幕语言是什么（有的频道人工字幕只有繁中或英文，但音频是别的语言）；
- 是整篇字幕还是逐词时间戳格式。

判断值得批量获取之后，大概的链路是这样：

1. 先用 `yt-dlp` 探测每个视频的字幕供给情况；
2. 下载视频与音频，人工字幕优先、自动字幕兜底；
3. 用 `ffmpeg` 抽出音轨，切成约 30 秒的片段；
4. 用 Qwen3-ASR 把音频重新转写一遍；
5. 把 ASR 转写和原始字幕比对，确认字幕语言与内容是否对得上；
6. 用字幕转写做切分对齐；
7. 送实体抽取。

这里最麻烦的其实是**字幕对齐**。人工字幕（CC）和自动字幕（ASR）的质量差异很大，而且不同语言的断句方式不一致。比较稳妥的做法是优先用人工字幕，没有再用自动字幕。

**一个我觉得挺有必要的中间步骤：把下载好的视频转成音频之后，用 Qwen3-ASR 自己再转写一遍，拿来跟原字幕比对。** 这有两个作用：

1. **验证字幕语言是否真的匹配**。这是踩过坑之后加的——有些视频的字幕是翻译版本（比如音频是中文、字幕是英译或台译），直接拿这种字幕去切分和对齐，得到的时间边界会整段错位；
2. **顺便筛掉字幕质量太差的片段**（自动字幕严重跑偏、音乐段落、纯 BGM 等）。

有了这层校验，后面送进实体抽取的都是"字幕与音频确实对得上"的片段，标注噪声会小很多。

另外字幕文件经常是「逐词时间戳」的格式（单词级时间轴），直接拿来当句子切分依据会切得很碎。我的处理是先把逐词时间戳合并成句子级，再做切分。

| 检索验证 | 每 9,095 优化步一次，K=1000 |
| early stopping | 以 val R@10 为准，patience 5 |

整套配置封装在一个启动脚本里，双卡直接跑即可；脚本支持断点续训，能从 `last.pt` 把模型、优化器、调度器、epoch 和 step 的完整状态都恢复回来，接着往下跑。

**关于有效 batch**：AmphionASR 论文里报告的是 6 卡、有效 batch 384。我这里只有 2 卡，有效 batch 128——这是配置上的差异，所以我的绝对指标不能直接跟论文对比，只能看趋势。单卡也能跑，但如果不把累积从 16 调到 32，有效 batch 会掉到 64，那就属于另一个实验了。

**关于 checkpoint**：训练 checkpoint 只保存 13 个 adapter/温度张量加续训状态，大约 20 MiB，不重复保存冻结基座。这一点很重要——早期版本每个 checkpoint 4.5 GiB，跑几十个实验下来磁盘直接爆掉。旧格式的完整 checkpoint 也仍然可以作为初始化权重读入，加载器会自动从中挑出 adapter 部分。

## 实验结果

### 检索验证（K=1000 候选池）

| epoch | 优化步 | val n | R@1 | R@5 | R@10 | R@20 |
|---:|---:|---:|---:|---:|---:|---:|
| 2 | 9,095 | 124 | 0.4919 | 0.7742 | 0.8226 | 0.8952 |
| **3** | **18,190** | **120** | **0.5167** | **0.8500** | **0.9417** | **0.9583** |
| 4 | 27,285 | 129 | 0.5349 | 0.7752 | 0.8450 | 0.8992 |
| 5 | 36,380 | 135 | 0.5926 | 0.8519 | 0.9111 | 0.9556 |
| 6 | 45,475 | 114 | 0.5702 | 0.8684 | 0.8772 | 0.9298 |
| 7 | 54,570 | 117 | 0.5897 | 0.8632 | 0.8974 | 0.9744 |
| 8 | 63,665 | 112 | 0.6250 | 0.9196 | 0.9375 | 0.9643 |

发布权重选的是 epoch 3 / step 18,190 那个点，也就是 **R@10 = 0.9417** 的 checkpoint。

这里有个值得注意的现象：**epoch 3 之后 R@1 其实还在涨，但 R@10 反而在波动**。最终我是按 R@10 来选的（early stopping 也是以它为准），因为在真实系统里这个召回模块的输出是要拼进 prompt 的候选列表，**top-10 能不能覆盖住真词比 top-1 精不精更重要**。

另外要提醒的是，每次验证进入统计的真实体数量只有 120 左右，样本很小，所以**单个 epoch 的 R@K 波动很大，不应该过度解读**。epoch 8 的 R@1 = 0.625 看着比 epoch 3 的 0.517 高不少，但这个差异未必显著。

还有一个容易混淆的地方：训练日志里的 `top1_local` 最后能到 0.9495，看着比 R@10 还高，但这个数字是 **batch 内对比命中率**（候选只有 batch 里的百来个负样本），跟 K=1000 的 R@K 完全是两回事，不能放在一起比。

### 早期实验轨迹（不同基座，仅供参考趋势）

这里要先做一个重要说明：下表这些早期实验用的**不是 Qwen3-ASR**，而是我最早搭的一版双塔——音频侧用 `Data2Vec-Speech`（`base_libri.pt`）、文本侧用 `bert-base-multilingual-uncased`。后来换成 Qwen3-ASR-1.7B 的音频塔 + token embedding 之后，才成为最终发布版。所以**下表的绝对数字不能和上面 Qwen3-ASR 的 R@K 直接对比**，只能看同一基座内部的趋势。

| 运行 | 数据规模 | epochs | 配置 | K=100 recall@1 |
|---|---|---|---|---|
| entity_bs8 | 实体 3万/语 | 10 | 单卡 bs8 | 0.171 |
| entity_10w_ddp14 | 实体 10万/语 | 14 | 双卡 DDP bs8×2×accum4 | **0.282** |

数据量扩大 3.3 倍 + 有效 batch 翻倍 + 双卡之后，recall@1 从 0.171 提到 0.282，**提升 65%**。中文部分的变化更明显：从小数据下的基本失效（0.003）变成可用（0.301）。这说明**数据规模对这个模块的影响非常大**，在预算允许的情况下优先加数据比调参更有效。

顺便一提，换到 Qwen3-ASR 基座之后，同一套数据上的检索指标又上了一个台阶（K=1000 下 R@1 0.5167 / R@10 0.9417）——**更强的冻结基座确实能把适配器的上限抬高**，这大概是整个项目里第二重要的结论。

## 评测协议的陷阱

这部分是我觉得最值得单独拿出来讲的。当你看到"recall@1"这种指标时，首先要问的是：**候选池有多大？**

下面这组数字来自早期那版 Data2Vec + BERT 的基座（`entity_10w_ddp14`），但"候选池大小决定指标量级"这个结论与基座无关，换到 Qwen3-ASR 上同样成立。同一个权重，在 K=100 和 K=1000 两个协议下的表现差异是巨大的：

| 候选池 | recall@1 | recall@5 | recall@10 | recall@100 |
|---|---:|---:|---:|---:|
| K=100 | 0.282 | 0.596 | 0.747 | — |
| K=1000 | 0.098 | 0.27 | 0.37 | **0.804** |

（上表为 `entity_10w_ddp14` 在项目内部 test 协议下的结果；K=1000 那一行来自随后的误召分析。两者的 query 数与采样方式一致。）

在 K=1000 的硬 top-1 协议下，误召率高达 **0.902**——也就是说 90% 的情况下排第一的都是错的。看到这个数字很容易得出"这模型没法用"的结论，但看 recall@100 = 0.804 就会明白，**模型的排序能力其实是有的，只是在上千个候选里，绝对的第一名很难保证是正确的那一个**。

进一步分析误召的词长分布也很有启发：**83.6% 的误召热词是单词短实体**（中文这个比例是 100%）。原因也不难理解——短词（尤其是单字/双字中文词）跟任何音频都容易撞出高分，因为它的语义和语音表征都太"泛"了。

所以我的结论是：**不应该用硬 top-1 来衡量这个模块**。它在千级候选池下的 top-1 几乎不可用（误召 90%），但 top-100 的覆盖能力是实打实的 80%。换句话说，它是一个明确的候选筛选模块，衡量它的正确方式是看 top-K 召回率，而不是看第一名对不对。

## 阈值标定：一个反直觉的发现

模块训练完之后要做 Web demo，需要给用户一个"这个词到底出没出现"的判断。我花了不少时间做阈值标定，这里有个比较反直觉的结论。

**先说无效的指标**：峰值 z-score 完全没用。实测真词的 z 值是 2.58 ± 0.47，干扰词是 2.51 ± 0.46——**两者完全重叠**，没有任何区分度。我一开始以为"峰值突出程度"能反映匹配质量，实测下来发现并不行。所以别用 z 值做判断。

**再说有效的指标**：余弦相似度的峰值和滑动窗口平均分。但这里的关键是：

> **阈值取决于音频长度，而不是语言。**

这个结论直接来自 max-over-time 的数学性质：**音频越长，取 max 的机会越多，随机词撞出高分的上限就越高**。实测数据：

| 音频类型 | 平均时长 | 真词 cos（均值±std） | 干扰词 p95 | R@1 |
|---|---:|---|---:|---:|
| 短朗读句 | 4.6s | 0.722 ± 0.040 | 0.670 | 0.966 |
| 会议 TTS | 14.1s | 0.697 ± 0.052 | 0.699 | 0.808 |
| 长会议 | 67s+ | — | **0.72+** | — |

可以看到：4.6 秒的短句，干扰词 p95 只有 0.670，阈值定 0.66 很安全；但到了 14 秒的会议音频，干扰词 p95 涨到 0.699，同一个阈值就会开始大量误报。

所以我的做法是**给每条 query 单独算一个"随机基线"**：在同一段音频上，用同语言的 N 个随机池词打分，取其中的最高分作为基线。然后用真实分数减去这个基线，用这个差值（我称之为"超出随机"）作为更可迁移的判断依据。因为它自动随音频长度变化，不需要为每种长度单独标定阈值。

不过绝对阈值仍然要保留作为参考，最终 UI 上的分档是这样的：

| cos 区间 | 判定 | 含义 |
|---|---|---|
| ≥ 0.72 | 高置信命中 | 基本可以确信出现了 |
| ≥ 0.66 | 较可能命中 | 大概率出现 |
| ≥ 0.60 | 弱匹配 | 可能有，需要人工确认 |
| < 0.60 | 证据不足 | 无法确认 |

注意最后一档我写的是**"证据不足"而不是"未出现"**。这个措辞是刻意选的：实测中真词在短对话句上也可能只拿到 0.56 左右。如果直接判"未出现"，会造成大量漏报。宁可说"我看不准"，也不要给出一个自信的错误结论。

### 帧到时间戳的映射

顺带记一个技术细节。音频塔每个 1 秒的 mel 块输出 13 帧，看上去像是稳定的 13 fps，但实际上**块内帧间隔是 0.04s、跨块是 0.08s**，是非线性的。

如果按均匀的 13 fps 去反推时间戳，在一段 15 秒的音频上会累积到接近 1 秒的误差——对于"定位这个词出现在第几秒"这个功能来说，1 秒的偏差是完全不可接受的。

正确的做法是直接反演厂商的长度公式：从第一个 mel 帧开始逐个往后扫，每当输出帧数比上一步增加，就说明产生了一帧，把此刻的时间记下来。这样每一帧都能拿到属于它自己的准确时间，而不是被网格近似掉。

## 踩过的坑

最后集中记录几个花了比较多时间才定位的问题。

### 1. 音频塔不能批量拼接编码

音频塔的前向只接受单条音频输入（128 维特征 × 时间长度），所以我一开始自然地想到：把多条音频按时间维拼起来一次编码，然后再切开，这样效率高一点。

结果是**错的**。音频塔内部用的是分块窗口注意力（推理时窗口大小是 800，编码时是 50），拼接之后窗口的划分位置变了，导致同一段音频在"拼接编码"和"单独编码"两种方式下的帧嵌入**差了大约 25%**。

所以只能逐条编码。这会明显变慢（实测从打包批量退回到逐条之后，单卡的吞吐大概降了一半以上），但数值必须是正确的——毕竟打分结果直接决定检索质量。

一个相关的验证结论是：**同一段音频重复编码是稳定的，批量编码 vs 单条编码的差异在 1.5e-7 量级**。也就是说问题不在批量本身，而在"拼接"破坏了窗口结构。所以如果只是把相同长度、独立的音频批处理（不拼接时间维），是安全的。

### 2. 日志里那些"看起来很好"的数字

最后提醒一个容易自嗨的点。训练日志里通常会有 `loss`、`global_loss`、`local_loss` 和 `top1_local` 这几个数字，我这边跑到后期大概是 loss 0.176、global_loss 0.008、local_loss 0.169、top1_local 0.9495 的样子。

这里的 `top1_local` 接近 0.95，看着很漂亮；`global_loss` 低到 0.008，更是让人觉得已经收敛了。但这几个数字都不能直接说明检索效果：

- `top1_local` 是 batch 内命中率，候选只有百来个；
- `global_loss` 已经低到 0.008，实际上说明全局分支的任务太简单了（整段音频对完整转写，本来就容易），这个分支的梯度贡献几乎消失了；
- 真正有意义的数字是**周期性在 K=1000 候选池上做的 R@K**。

所以我的建议是：**训练期间就把检索式验证挂上**（我这个项目是每 9,095 步跑一次），并且 early stopping 直接盯 R@10，而不是盯 loss。否则很容易在一个"loss 很漂亮但检索没用"的 checkpoint 上浪费大量时间。

## 小结

整理一下我认为比较重要的几点：

1. **max-over-time 是这个模块的灵魂**。它把"整段匹配"变成"存在某段匹配"，让长音频里的短热词也能被捞出来。但代价是阈值会随音频长度漂移。
2. **负样本设计决定上限**。从 in-batch 换成池负样本（同语言、batch 共享、排除真词）是效果提升的主要来源；单向子串安全和实体冲突 batch 则是避免假负样本的必要工程手段。
3. **数据质量 >> 数据技巧**。真实实体标注的效果比随机子串高一个数量级，这是整个项目里最大的一个结论。
4. **评测协议要写清楚**。同一个模型在 K=100 和 K=1000 下的 recall@1 能差 3 倍，脱离协议谈指标没有意义。
5. **注意那些静默的错误**：温度存成 0.07、拼接编码破坏窗口结构、用翻译字幕去做对齐——这些都不会让程序崩溃，但会让实验结论完全失真。

以上都是一家之言，很多结论是基于有限的实验观察，没有做严格的消融对照。欢迎指正。
